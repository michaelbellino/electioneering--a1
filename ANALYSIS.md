# Election Games — High-Detail Analysis Pass

An audit of the games packaged in this repo, focused on **what the code actually does under
the hood** versus what the player (or the docs) is told. The prompt's example — *"the background
options don't tell you what they do or what the point of them is"* — turns out to be the tip of a
much larger iceberg: both games are full of mechanics, formulas, and content that are either
**hidden from the player** (Stateline) or **fully specified but never implemented** (Campaign
Trail).

> **Where the code lives.** The repo root contains only `electiongames.zip` and
> `a1electioneeringa1.bundle` (identical content; bundle ref `claude/ecstatic-dirac-rju297`).
> All source discussed below is *inside* the zip, under three subprojects:
> `stateline/`, `campaign-trail/`, and `claude-code-game-studios/`. Paths in this document are
> relative to the archive root.

---

## TL;DR — the headline findings

1. **The "background options" are candidate stats that silently drive a hidden utility model.**
   In **Stateline**'s candidate creator, the four **Attributes** sliders (Charisma, Competence,
   Integrity, Fundraising) and the eight **Platform** sliders have *zero* on-screen explanation.
   They feed concrete formulas the player never sees (§2). Integrity, in particular, is almost
   cosmetic. In **Campaign Trail** the three candidate **archetypes** ("backgrounds") carry
   detailed numeric `startingModifiers`, but no engine exists to apply them (§6).

2. **Stateline's election night is deterministic.** The jittery polls are theater; the actual
   result is a pure function of your end-state. Randomness only ever breaks an *exact* whole-ballot
   tie (§3). The game's own test asserts that simply acting each week **wins the "tossup"** — it's
   close to un-losable (§3.4).

3. **Several Stateline systems are defined but inert** — scandal, campaign strategy/tone,
   the `persuasion` effect channel, incumbency, per-segment ad targeting, and one of three RNG
   streams all exist in the types/state but are never read by any logic (§4).

4. **Stateline's "real Census data" is provisional, hand-authored placeholder data**
   (`provisional: true`, `dataVersion: 'seed-0.1.0'`). Real ACS numbers only appear if you run the
   ETL with a Census API key. Three of the four bundled districts are unreachable content (§5).

5. **Campaign Trail is not runnable.** Its `ARCHITECTURE.md` promises `engine.js`, `ui.js`,
   `main.js`, `index.html`, and `test/sim.js` — **none of which exist in the bundle.** Only the
   RNG, helpers, SVG chart/map renderers, and the content data shipped. The whole simulation lives
   as *prose* inside `data.js` (§6). Its "Pre-Delivery Checklist" is all ✅ for an app that can't open.

6. **Campaign Trail's numbers don't reconcile** (§8.3). Each region ships **two** electoral-vote
   fields (one summing to 328, one to 538); the regression-to-baseline mechanic reads a
   `regionBaseline` field **that isn't in the data**; and the balance notes say the player starts at
   ~235 EV when the actual board puts them at **295 EV — already past 270 at turn 0** — with **zero**
   "safe" (lean ≥ 40) regions despite the tutorial telling you to ignore them.

7. **The inert fields are footprints of a much bigger design.** Stateline ships a raw multi-agent
   design spec (`docs/design/architecture-fanout.raw.json`) describing opinion dynamics, an effects
   graph, an economy, and a whole legislature — the built slice is a simplified subset, and the dead
   scaffolding is what's left of the rest (§9). One concrete gap: the roadmap lists "diminishing
   returns" as a done Phase-1 feature, but the code has none (ad spam stacks linearly).

## 2. Stateline — what the "background options" actually do

The creator (`src/ui/screens/CandidateCreator.tsx`) shows four Attribute sliders and eight Platform
sliders with a one-line hint ("−1 conservative · +1 progressive") and nothing else. Here is the
machinery they drive.

### 2.1 Attributes → **valence** (candidate quality)

`src/engine/campaign/profile.ts`:

```
valence = clamp01( 0.3 + 0.4·charisma + 0.3·competence + 0.1·integrity − 0.25·scandalLoad )
```

- **Charisma** is the strongest attribute (coefficient 0.4) — and it *double-dips*: it also
  amplifies every `event`-category action by `+charisma·0.3` (`actionMultiplier`, §2.3).
- **Competence** is worth 0.3.
- **Integrity** is worth **only 0.1**, and is used *nowhere else* in the engine. Sliding it from 0
  to 1 moves valence by 0.1, i.e. ~0.09 of final vote utility (valence weight is 0.9). It is very
  nearly a decorative slider.
- **scandalLoad** would subtract 0.25 — but it is hard-wired to `0` and nothing ever raises it (§4).

Worked values (with scandal 0):

| Charisma / Comp / Integ | Valence |
|---|---|
| 0 / 0 / 0 | **0.30** (floor) |
| 0.6 / 0.6 / 0.6 (creator default) | **0.78** |
| 1 / 1 / 1 | 1.10 → clamped to **1.00** |

Valence then enters vote choice with weight **0.9** (`MODEL_WEIGHTS`, `src/engine/electorate/model.ts`).
**The player never sees their valence number** — the dashboard shows only Name-rec and Favorability.

### 2.2 The "Fundraising" attribute → money, two ways

`src/engine/campaign/logic.ts`:

- **Event yield:** `fundraiseMultiplier = 1 + fundraising·0.8 + fundraiserStaff·0.6`.
  A "Host a Fundraiser" action (base **$40,000**) at the default 0.5 fundraising and no staff pays
  `$40k × 1.4 = $56,000`.
- **Passive weekly trickle:** `round((20000 + 80000·fundraising) · weeks)` cents.
  That's **$200/week at fundraising 0 → $1,000/week at fundraising 1** (small-dollar income).

### 2.3 Attributes → action effectiveness

`actionMultiplier = 1 + (staffEffectiveness·0.5) + (offices·0.05) + (event ? charisma·0.3 : 0)`,
where `staffEffectiveness` is the summed effectiveness of matching-role staff, **capped at 1.5**.
So charisma quietly makes rallies/debates hit harder, and field offices add +5% each to whatever
action they amplify.

### 2.4 Platform (the 8 issue sliders) → **spatial proximity**

`src/engine/electorate/evaluate.ts`, `groupUtility`:

```
proximity(group, cand) = −( Σ salience·(groupPos − candPos)²  /  Σ salience )   ∈ [−4, 0]
```

Each of six demographic groups has its own issue positions **and its own salience weights**
(`src/data/voterModel.ts`) — e.g. white-noncollege voters weight immigration ×1.4 and guns ×1.3;
Black voters weight crime/policing ×1.4 and healthcare ×1.3. So the *same* platform move helps you
with some groups and hurts you with others, weighted by how much each group cares. None of this is
surfaced; the creator doesn't tell you which issues matter to whom, or even that groups exist.

### 2.5 The full vote-choice model (never shown anywhere)

```
utility(group, cand) = 1.0·proximity + 2.6·(strength·effLean·partyDir) + 0.9·valence + 0.9·favorability
voteShare(group)     = awareness_c · exp(utility/0.55)  ÷  Σ_c (…)      // awareness-gated softmax, τ=0.55
```

Consequences the UI hides:

- **Partisanship dominates (weight 2.6).** It dwarfs valence and issues. US politics is
  partisanship-first by design — but it means your carefully-tuned platform is a minor term.
- **Awareness gating is brutal.** `awareness = 1 − e^(−exposure)`. A candidate with awareness 0
  gets **zero** votes regardless of quality. Your created candidate starts at exposure 0.1 →
  **awareness ≈ 0.095**, while the scripted opponent starts at exposure 0.6 → **≈ 0.451** (about
  **4.7× your name recognition**). Most of the game is just closing that gap.

### 2.6 The **Party** dropdown is the most consequential "option" of all

`partyDir` is `+1` for D, `−1` for R, **`0` for Independent**. Because the partisan term carries
weight 2.6:

- **Pick Independent →** the single largest term in the utility function is **zeroed for you** while
  your opponent keeps theirs. On top of that, GOTV/canvassing does nothing for you: `deriveTurnoutBoostMap`
  (`profile.ts`) early-outs when `partyDir === 0`. Independent is a silent hard-mode.
- **Pick Republican →** you become an R, **but the scripted opponent "Dale Whitaker" stays an R too**
  (the creator only overrides *your* candidate; see `gameStore.startGame` merging
  `{...HOUSE_SPECIAL_PA07.player, ...you}` and leaving `opponent` untouched). Now both candidates
  share `partyDir −1`, the partisan term becomes a wash between you, and the race silently collapses
  to valence + platform + favorability + awareness in a district calibrated to lean slightly D.

The dropdown looks cosmetic. It reshapes the entire model.

## 3. Stateline — the deterministic election (the biggest "unseen" truth)

### 3.1 Polls are noisy; the result is not
`src/engine/electorate/polling.ts` adds Gaussian sampling noise (n=600 → reported **±4 pts**;
`marginOfError = 1.96·√(0.25/600) ≈ 0.04`) from a **forked** RNG stream, purely so the poll line
wiggles. But `src/engine/electoral/resolve.ts` computes the actual winner from
`evaluateElectorate`, which is **pure and RNG-free**. The only randomness on election night is a
seeded coin flip to break an **exact integer-vote tie** (`allocators.ts`, `allocateFPTP`).

**Implication:** if your true share leads on the final day, you win with probability 1. The
suspense on the polling chart is cosmetic.

### 3.2 GOTV never shows up in the polls
`conductPollRecord` (`reducer.ts`) evaluates **without** the turnout boost, while the real
`resolveElection` applies it. So canvassing ("Canvass & GOTV", `turnout +0.03`) can win you the
election **without ever moving your poll numbers** — the one action whose payoff is invisible even
in the fake polls.

### 3.3 The opponent AI isn't an AI
`opponentEffects` (`reducer.ts`) emits a **fixed** schedule every week regardless of anything you do:
`nameRecognition += 0.35` (half-life 30d) and `favorability += 0.028` (half-life 21d), scaled by
`aiOpponentIntensity = 0.35`. It never reacts, never targets, never spends money. The `rng.ai`
stream allocated in `scenario.ts` is **never used**.

### 3.4 The game is nearly un-losable
`src/engine/e2e.test.ts` asserts *"out-campaigning a passive opponent wins the tossup"*: running just
three actions a week beats the passive opponent deterministically at the tested seed. Between the
non-reactive opponent and the deterministic resolver, a player who simply clicks actions each week
wins the "genuine tossup" almost every time.

### 3.5 Timeline & economy (also unstated)
Jun 2 → Sep 15 2026 = **15 weekly ticks**; **3 action points/week** (~45 actions total). Starting
cash **$50,000**. TV ads have **no cooldown**, so with cash + AP you can spam them; rally/canvass are
7-day, fundraiser 5-day, speech 3-day.

## 4. Stateline — defined-but-inert systems (dead scaffolding)

Verified by tracing every read site (`grep` for each symbol's consumers). These exist in
types/state and are written, but **no gameplay logic ever reads them**:

| System | Where it's defined / written | Why it's inert |
|---|---|---|
| **Scandal** (`scandalLoad`) | `valenceOf` (−0.25·), `deriveCandidateProfile` (−0.3· on favorability) | `createCandidate` hard-codes `0`; no event/action ever raises it. Both formulas always multiply 0. |
| **Campaign strategy** (`tone`, `focusIssue`) | `campaign/setStrategy` action stores them | Nothing reads `campaign.strategy`; no UI dispatches it. Pure no-op. |
| **`persuasion` channel** | `EffectChannel` union; issue/tone fields on effect target | No action emits it; `evaluate` never consumes it. Placeholder for a future messaging system. |
| **Message `tone`** | Copied onto effects in `pipeline.ts` | No consumer reads `target.tone`. Cosmetic metadata. |
| **Incumbency** (`incumbent`) | `CandidateProfile.incumbent`, `deriveCandidateProfile` opt | Always `false`; `groupUtility` ignores it entirely. |
| **Per-segment ad reach** (`segmentWeights`) | `EffectTarget.segmentWeights` | No action sets it; `sumElectorateChannel` ignores it → all effects are electorate-uniform. |
| **`rng.ai` stream** | Allocated in `createGame` | Never referenced again. (Of three streams, only `polling` does real work; `events` only breaks ties.) |

None of this is *wrong* — it's forward-scaffolding for the roadmap's Phase 2/3 — but a reader/player
has no way to know these knobs currently do nothing.

## 5. Stateline — the "real data" caveat

`src/data/datasets/demographics.seed.ts` is explicit in its own header: the figures are
**"approximate seeds (`provisional: true`) authored to be realistic, not exact."** `dataVersion` is
`'seed-0.1.0'`; every jurisdiction carries `provisional: true`. The README's headline ("built on
**real Census demographics**") is only true *after* a developer runs
`CENSUS_API_KEY=… npm run etl:demographics` to overwrite the snapshot. As shipped, the game runs on
plausible-looking hand numbers.

**Unreachable content:** the snapshot defines four jurisdictions — `us-pa` (statewide),
`us-pa-cd07`, `us-ny-cd13` (safe-D), `us-tx-cd13` (safe-R) — but the only scenario
(`HOUSE_SPECIAL_PA07`) and the `MainMenu` hard-wire **PA-07**. NY-13 and TX-13 are fully authored,
calibrated, and **impossible to play**. The calibration machinery (`build.ts` bisects a
`calibrationOffset` so the model reproduces each district's lean) runs against data no player can select.

## 6. Campaign Trail — a fully-designed game with no engine

### 6.1 What's missing
`docs/ARCHITECTURE.md` specifies this file layout:

```
index.html   engine.js   ui.js   main.js   test/sim.js   +  rng.js util.js charts.js map.js data.js
```

The bundle contains **only** `src/{rng,util,charts,map,data}.js` (plus CSS/docs). There is **no
`index.html`, no `engine.js`, no `ui.js`, no `main.js`, no `test/`.** So:

- Nothing wires the modules together; nothing to open in a browser.
- The documented public API (`Campaign.Engine.create/doAction/endTurn/tally/checkEndConditions/save`)
  **does not exist** — `Campaign.Engine` is never defined. Present namespaces are only
  `RNG`, `Util`, `Charts`, `MapView`, `Data`.
- `docs/DESIGN.md`'s "Pre-Delivery Checklist" is entirely checked ✅ for a UI that has no app to render it.

### 6.2 The whole simulation exists as prose in `data.js`
The rules are written as human-readable strings the (absent) engine was meant to implement. Examples:

- **Turn upkeep** (verbatim `effectSummary`): *"apply momentum drift to all leans (lean += momentum·0.05)
  … regress each region 12% toward (regionBaseline + nationalApproval·0.10), at half rate for
  'organized' leans; if scandalLevel > 40 subtract (scandalLevel−40)/10 … decay momentum 20% toward 0 …
  apply ±2.5·N(0) volatility jolt to up to 2 contested regions."*
- **Opponent AI** is described as a "weighted-priority planner" (~200→340 funds/week × difficulty,
  5 AP, at most 2 regions/week, effectiveness `×(1 + opponentMomentum/200)` suppressed by
  `×(1 − opponentScandal·0.005)`) — again, **only as text**.
- 16 actions (`tv_ad_blitz`, `attack_ad`, `build_field_office`, `opposition_research`, …), **34
  branching events** (with `triggerWeight`, categories like `leaked-tape`, and per-choice effects),
  10 effect channels, and 6 `regionLean` selectors (`all/strongest/weakest/random/mostVotes/none`) —
  all inert data.

### 6.3 The "background options": three candidate archetypes
`data.candidates` defines Dana Reyes **(The Charismatic Outsider)**, **The Seasoned Insider**, and
**The Grassroots Organizer**, each with a paragraph of `startingModifiers`. Unlike Stateline, these
*are* documented in the data — e.g. the Outsider *"Starts with +20 National Momentum and +15 Media
Buzz but only 4 volunteers (vs 8); Rally/Debate gains +20%, viral chance +5%; counterweight:
ground-game 15% less effective, rally gaffe 12%→18%."* But with no engine, **nothing reads these
either** — same end result as Stateline: the choice's effect is unknowable in play because there is
no play.

### 6.4 Other granular tells
- **Content is synthetic.** `data.js` header: content came from a "judge-panel of 3 proposals →
  synthesis → parallel generation" workflow. Region names are fictionalized states (`calforna`,
  `texano`, `floridia`, `new_yorke`, `pennsylvia`, `ohiola`, …) with invented abbreviations.
- **The EV total was patched.** Regions originally summed to **328 EV**; a post-process scaled them
  to exactly **538** to preserve the 270/538 identity (`meta.evFix`). Per-region EV are therefore
  synthetic, scaled figures, not real allocations.
- **The game starts already won.** `meta.projectedStart` is player **295** vs opponent **243** —
  above the 270 line before turn 1 — flagged "subject to empirical tuning in the verify phase" that
  (with no engine or tests) never happened.
- **Config:** 12 turns, **5 AP/turn (never banked)**, starting funds 1200, 18 regions, 3 candidates.

### 6.5 What *is* built (and is real)
`rng.js` (seeded mulberry32 + FNV-1a, same family as Stateline's), `util.js`, `charts.js`
(hand-rolled SVG line/bar/spark/gauge/donut), `map.js` (SVG cartogram), and `styles.css` (a
genuinely complete, tokenized, WCAG-AA dark "war-room" design system). It's a polished shell and
content pack around a missing core.

## 7. Cross-cutting theme

Both games fail the prompt's test — *"the options don't tell you what they do"* — but for **opposite
reasons**, which is the interesting part:

- **Stateline**: the mechanics are **implemented and correct but hidden.** The UI exposes exactly two
  numbers (name-rec, favorability) and a noisy poll, while valence, proximity, turnout, calibration,
  and the deterministic true result stay backstage. The sliders work; you just can't see or feel most
  of what they do.
- **Campaign Trail**: the mechanics are **documented in exhaustive numeric detail but not
  implemented.** Every formula, action, event, and archetype modifier is specified in `data.js`/docs,
  and there is no engine to run any of it.

## 8. Campaign Trail — the full mechanics that never run

Everything below is real content in `src/data.js` that the (absent) engine was meant to execute.
It's worth cataloguing because it shows how *complete* the design is and how *inconsistent* some of
the numbers are — inconsistencies no runtime ever forced anyone to reconcile.

### 8.1 The 16 actions (exact costs & effects)

| Action | Funds | AP | Target | Core effect (from `effectSummary`) |
|---|---:|---:|---|---|
| TV / Social Ad Blitz | 180 | 1 | region | lean `+12 · (1+momentum/200) · (1−max(0,scandal−30)·0.005)`, floor +3; **4th+ buy in a region = 60%** |
| Attack Ad | 140 | 1 | region | lean `+9·momMult`; opp momentum −6, opp scandal +5; **your scandal +3** |
| Build Field Office | 120 | 2 | region | lean +6 now **+ passive +3/turn** (×volunteers/10), "organized" (regresses 50% slower); +3 volunteers |
| Volunteer Canvass | 40 | 1 | region | lean `+(5 + volunteers·0.6)·momMult`, "organized"; +1 approval |
| Recruit Volunteers | 150 | 1 | national | +8 volunteers (+2 if buzz>40); +0.4 passive lean/turn to already-winning regions |
| Campaign Rally | 90 | 2 | region | lean +6·momMult; momentum `+10+buzz·0.05`, buzz +8; **viral roll `0.10+buzz·0.003`** doubles gains; **12% gaffe → scandal +3** |
| Major Fundraiser | 0 | 2 | national | funds `+round((220 + momentum·2 + approval·3)·(1+buzz·0.01))`, floor 150; momentum −3 |
| Opposition Research | 110 | 2 | national | **75% success**: opp scandal +18, opp momentum −8; **backfire: your scandal +12** |
| Damage Control | 80 | 1 | national | scandal `−20`; buzz −4; if scandal was >50 also momentum +4 |
| Debate / Media | 100 | 2 | national | if scandal<40: approval +5, momentum +6, buzz +16; else 45% chance scandal +10 & momentum −5 |
| Counter-Messaging | 100 | 1 | national | opp momentum −12 (+50% if it was >40); your momentum +3, buzz +2 |
| Polling Consultant | 100 | 1 | national | reveals opponent targets + region baselines; next region action +25%; no stat effect |

(`funds` are in $1,000s; starting war chest 1,200 = $1.2M. 5 AP/turn × 12 = **60 lifetime AP**, never banked.)

### 8.2 Win / fail thresholds (all hardcoded in data, none enforced by code)

- **Win:** hold ≥270 of 538 EV on turn 12; **early clinch** if lean≥40 regions ≥270 and opponent can't
  reach 270; **opponent collapse** if `opponentScandal ≥ 90 AND opponentMomentum ≤ −40`.
- **Fail:** <270 on election day; **bankruptcy** if `funds ≤ 0 AND volunteers < 3 AND momentum < 0`
  (grace-protected); **scandal collapse** at `scandalLevel ≥ 80`.
- **Difficulty** (`strengthMultiplier`): easy ×0.7 budget/×0.8 gains; normal ×1; hard ×1.3 budget/×1.15
  gains, +5 opponent lean in 4 high-value regions, aggressive oppo-research.

### 8.3 Concrete data inconsistencies (found by summing the actual rows)

These are the kind of "unseen details" that only surface when you total the numbers:

1. **Two electoral-vote fields per region.** Each region carries both `baseElectoralVotes` (the
   original synthetic values, which sum to **328**) and `electoralVotes` (scaled ×`538/328 ≈ 1.64`,
   which sum to exactly **538**). A single mis-referenced field (base vs scaled) silently breaks the
   270/538 math. The header note ("regions originally summed to 328; scaled to 538") is accurate — but
   both numbers ship on every region with nothing marking which one is live.
2. **The regression target doesn't exist in the data.** Turn upkeep and the win check both regress /
   read `regionBaseline` (the structural lean each region drifts toward), but **no region row contains
   a `baseLean`/`baseline`/`regionBaseline` field** — only `initialLean`. The central
   regression-to-mean mechanic has no data to read.
3. **Field names don't match the documented state model.** `ARCHITECTURE.md`'s `GameState.regions[]`
   uses `lean` + `baseLean`; the data uses `initialLean` and no baseline. An engine would have to
   translate between spec and data that were never reconciled.
4. **The balance prose contradicts the shipped board.** `balance.notes` says the player *"begins
   around 235 projected EV"* and that there are *"~5 safe-player regions (lean +25..+40, ~120 EV)."*
   Summing the actual `initialLean` values: the player leads (lean>0) in regions worth **exactly 295
   EV** (matching `meta.projectedStart`, not 235) — i.e. **already past 270 at turn 0** — and **zero**
   regions start at lean ≥ 40. So the `win_early_clinch` rule and the tutorial's *"Safe regions (lean
   over +40) don't need your money"* describe a state that does not exist at kickoff.
5. **One region is 90 EV** (Calforna) — 16.7% of the whole college in a single tile, larger than any
   real state — an artifact of forcing 18 regions to sum to 538. Texano is 62.
6. **Per-region `volatility` (0.15–0.2) vs global `baseVolatility` (2.5)** are never reconciled; the
   upkeep text applies a flat `±2.5·N(0)` and ignores the per-region field.

## 9. The grand-design-vs-slice gap (why the dead code exists)

Stateline ships a raw multi-agent design artifact: `docs/design/architecture-fanout.raw.json`. It
specifies a system **far** larger than the built slice — and reading it explains almost every inert
field flagged in §4. The spec calls for:

- **Opinion dynamics** with exponential smoothing/inertia (favorability drifting toward targets driven
  by ad tone, media diet, endorsements, scandals; thermostatic mood).
- A **Democracy-4-style effects graph** (`SimNode`/`SimEdge` with transfer functions and feedback
  damping) — the real ledger is a flat additive list instead.
- **Economic indicators** + partisan motivated reasoning; **hazard-rolled scandals**; fatigue /
  stamina / morale; scheduled-vs-instant actions; per-segment ad reach; diminishing-returns history;
  identity & incumbency bonuses.
- A full **governing/legislature** subsystem (state-machine process, AI legislators, whip counts,
  logrolling) and **RCV / two-round / party-list / Electoral College** allocators.

The built engine implements a clean, simplified subset. The leftover type fields — `persuasion`,
`segmentWeights`, `incumbent`, `scandalLoad`, `strategy.tone/focusIssue`, the `governing` phase, the
richly-featured event queue used for one event, the third `ai` RNG stream — are the **footprints of
that spec**, stubbed into the slice as forward-hooks for roadmap Phases 2–3. So the "dead code" is
deliberate scaffolding, not bugs — but nothing in the app tells a reader that.

### 9.1 Two concrete doc-vs-code discrepancies

- **"Diminishing returns" is claimed but not implemented.** `roadmap.md` lists Phase-1 actions as
  having *"cash/action-point costs, cooldowns, diminishing returns."* Cooldowns exist; **diminishing
  returns do not** — `pipeline.ts` computes `magnitude = spec.magnitude · multiplier` with no
  per-action buy history, and positive TV ads have a **0-day cooldown**, so ad spam stacks perfectly
  linearly. (Ironically, Campaign Trail's data *specifies* diminishing returns — "4th+ blitz at 60%" —
  but has no engine to apply them. Neither game actually runs the feature.)
- **Unused math helpers.** `primitives.ts` exports `sigmoid` and `softmax`, but the vote model rolls
  its own inline awareness-gated softmax and never calls either; both are dead utilities.

### 9.2 Where the docs *are* honest

Worth stating plainly: Stateline's **deep** docs do disclose the caveats the UI hides.
`docs/data-pipeline.md` says the snapshot is provisional and *"not real data"* until a keyed ETL run,
and the design fan-out states the polling layer exists *"so the player never sees ground truth"* while
*"utility/turnout/share math is fully deterministic."* The honesty gap is between the **top-level
README / in-app UI** ("built on real Census demographics", unlabeled sliders) and the **buried design
docs** — not a contradiction inside the docs themselves.

## 10. Provenance — these games were generated by the bundled studio

The third subproject, `claude-code-game-studios/` (CCGS), is a 49-agent / 73-skill Claude Code
"studio" (creative-director, economy-designer, engine specialists, QA, etc.). Both games carry its
fingerprints: Campaign Trail's `data.js` header credits a *"judge-panel of 3 proposals → synthesis →
parallel content generation"* workflow, Stateline ships the raw *architecture-fanout* design artifact,
and Campaign Trail vendors a `ui-ux-pro-max` skill whose design system produced its (genuinely
polished) CSS. This is why both games look like *the plan is more finished than the game*: the
generation pipeline produced exhaustive design + content + a tuned visual system, and the actual
